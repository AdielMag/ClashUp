The runtime UI is being migrated from hand-built legacy UGUI to **UI Toolkit** using a supplied design ("3v3 Auto-Battler", originally in `Downloads/# 3v3 Auto-Battler UI Framework`). Unity 6.0.76f1 — UI Toolkit runtime is built-in (no manifest change). Started 2026-06-30.

## Foundation (Phase 0)
- **UXML/USS/theme** live in `Assets/Resources/UI/` (Resources so the runtime `.Create()` factories can `Resources.Load<VisualTreeAsset>("UI/<Screen>")`). Files: `Theme.uss`, `AppTheme.tss`, `LoadingScreen`, `LobbyPlay`, `CharacterSelect`, `InGameHUD` (`.uxml`+`.uss`). USS `<Style src="Theme.uss">` is relative (same folder).
- **Sprites** (placeholder art from the design): `Assets/Resources/Sprites/{HUD,Loading,Lobby,UI}/`. USS refs them via `resource("Sprites/...")`. 9-slice handled by USS `-unity-slice-*` (no importer borders needed).
- **Fonts**: `Assets/Resources/Fonts/Fredoka-SDF.asset` + `Nunito-SDF.asset`. **CRITICAL**: UI Toolkit `-unity-font-definition: resource("Fonts/..")` needs a **`UnityEngine.TextCore.Text.FontAsset`**, NOT `TMPro.TMP_FontAsset` (that's the TMP/UGUI type — produces "Font not found"). Generated via `UnityEngine.TextCore.Text.FontAsset.CreateFontAsset(font,…)` (script-execute) from the TTFs, persisting atlas+material as sub-assets. **CRITICAL #2**: use a **BOLD/SemiBold STATIC** TTF as the source. The variable `Fredoka[wght]`/`Nunito[wght]` TTFs import at their *lightest* axis (Light/ExtraLight) → hairline text that looks nothing like the chunky design (this caused a "doesn't look the same at all" regression). Fixed by regenerating from `Fredoka-SemiBold.ttf` (600) + `Nunito-Bold.ttf` (700) static instances (Fontsource CDN `cdn.jsdelivr.net/fontsource/fonts/<fam>@latest/latin-<wght>-normal.ttf`); the variable TTFs were deleted so the SDF can't regen thin. The chunky look needs both the weight AND the USS `-unity-text-outline-*` comic outline (works on SDF).
- **PanelSettings**: `Assets/Resources/UI/MainPanelSettings.asset` — ref res 1080x1920, ScaleWithScreenSize, MatchWidthOrHeight=1 (portrait). References `AppTheme.tss` (a `@import url("unity-theme://default")` ThemeStyleSheet). Shared by every screen.
- Helper [UiToolkitRoot.cs](../../client/ClashUp.Unity/Assets/Core/UI/Scripts/UiToolkit/UiToolkitRoot.cs) (`ClashUp.UI`): `LoadTree(path)` + `CreateDocument(name,tree,sortingOrder)` spawns a configured `UIDocument` GameObject. `Order` constants for layering. `ClashUp.Lobby.asmdef` now references `ClashUp.UI`.
- Runtime UIDocument tree is populated **synchronously** right after assigning `visualTreeAsset` — bind elements immediately, no deferred schedule needed.

## Source of truth = the HTML artifact, NOT the UnityExport port
The real design is the **HTML artifact** `Downloads/# 3v3 Auto-Battler UI Framework (1)/Auto-Battler UI Framework.dc.html` + `screenshots/s1..s4.png` (both exist on disk at that exact path — `s3.png` = Character Select, `s4.png` = in-game HUD). The `UnityExport/` UXML+USS that shipped alongside is a SIMPLIFIED port pointing at crude placeholder PNGs — it does NOT match the mock (e.g. `lobby_bg.png` placeholder is a sun/cloud sky, but the mock background is a CSS **gradient**). When matching the look, read the HTML's inline CSS, not the UnityExport USS.
- **The HTML file itself has TWO different CSS sources for the same screen — they can disagree, and neither alone is complete**: (1) an interactive **live preview** (small ~288px-wide phone frame, actual rendered HTML/CSS, representing the 1080px reference width at a ~3.75× scale-down) which shows the REAL visual intent, and (2) an embedded **"UnityExport" code block** (`<pre class="codescroll">` with HTML-escaped `&lt;ui:...&gt;` UXML/USS text) meant to be the literal Unity spec. The code block can be missing structural details the live preview has (e.g. Character Select's `.stat-val`/`.stat-cap` code-block classes have NO background pill at all, but the live preview clearly renders the stat icon+value inside a white rounded pill — `.stat-pill` had to be invented to match the preview, the code block alone would have produced a wrong result). When they conflict: trust the code block for exact numeric values it DOES specify (font-size, spacing) since those are verified-accurate reference-res numbers; trust the live preview for structural/visual details the code block omits. Best practice: pull up `screenshots/s1..s4.png` directly and compare pixel-by-pixel against a live in-editor screenshot (see [[unity-mcp]] "Screenshotting a Runtime UI Toolkit Screen") rather than only reading CSS — it's faster and catches things CSS-reading misses.
- **Backgrounds are gradients** (USS can't do gradients). Generated vertical-gradient PNGs via script (`Texture2D`+`EncodeToPNG`, 270x480) and overwrote `lobby_bg.png` (`#5BC8FF→#6E7BF0→#8A5BE0`) and `select_bg.png` (`#6E5BD0→#5B7BE0→#3FA9C4`). Regenerate the same way if restyling.
- Lobby: added translucent **`.hero-preview` "CHARACTER" card** placeholder (real look needs the hero RT) + `.deco-circle`; mode sub = "BRAWL BALL".
- Character Select: stat values sit in white **`.stat-pill`** (icon tinted hp=#FF3B5C/atk=orange/spd=teal, dark value, caption below) — the UnityExport USS had no pill bg.
- Lobby + Character Select now closely match s2/s3. Remaining nicety: UI Toolkit borders can't be dashed (mock hero card uses a dashed stripe), so the placeholder card uses a solid translucent border. In-game HUD (s4) not yet re-matched to the mock.

## USS gotchas hit while matching the mock
- **Pill/capsule shape**: don't use `border-radius: 999px` on a wide, short element — UI Toolkit draws *stretched elliptical* corners (the currency pills looked like ovals). Use `border-radius = half the element height` for clean semicircular ends.
- **Default Button chrome**: Unity's `.unity-button` ships a gray border + background + margin. It showed as gray boxes around nav tabs and a frame behind BATTLE. A global `.unity-button { border-width:0; margin:0; padding:0; background-color: rgba(0,0,0,0); }` reset in Theme.uss fixes it (our buttons define their own look).
- **Sizing — USE THE HTML's USS CODE BLOCKS VERBATIM, do NOT ×3.75 the screenshots.** The `<pre class="codescroll">` blocks in `Auto-Battler UI Framework.dc.html` are written at the **1080×1920 reference resolution** = the real spec. The earlier "multiply mock px by 3.75" approach OVERSHOT (e.g. battle-btn ended up 116px vs the spec's **76px**; mode-title 56 vs **38**; nav-label 34 vs **22**; HUD score-num/ timer were inflated too). Re-transcribed all four screens (lobby/select/HUD lines ~522/773/968; loading ~289) to the exact code-block values. Key authoritative sizes: battle-btn 76 (slice 60/60/40/64, h150), mode-banner h96 r24, mode-title 38, mode-sub 22, nav-bar h180 r36, nav-icon 56, nav-active-icon 118, level-badge 120, coin/gem pill r=half-height; cs-title 48, hero-name 64, stat-val 32, stat-cap 18, hero-card 200×240 r24, select-btn 72; HUD gear 96, score 96×84, score-num 54, timer 40, scoreboard r22 bw4; loading-text 64.
- **Type scale + font assignment** (the "fonts look wrong" fix): design = **Display Fredoka 700/64, Title Fredoka 600/44, Body/Label Nunito 800/30, Caption Nunito 700/22**; the page's default `font-family` is **Nunito**. Many elements use `-unity-font-style: bold` with NO `-unity-font-definition` → they were falling back to the engine default font (generic sans), not Nunito. Fix: set `-unity-font-definition: resource("Fonts/Nunito-SDF")` on **each screen ROOT** (`.lobby-root/.select-root/.hud-root/.loading-root`) — font properties INHERIT in UI Toolkit, so all body/label text becomes Nunito; elements that set Fredoka explicitly (display/title: battle-btn, select-btn, cs-title, hero-name, score-num, hero-card-name, loading-text) override. `Fonts/Nunito-SDF.asset` already exists (TextCore FontAsset from `Nunito-Bold.ttf`).
- **Glossy buttons**: generated 9-slice button sprites (vertical gradient + top sheen + baked dark bottom lip) via script for `btn_battle_9s`/`btn_select_9s`/`btn_mode_9s` (200x140, slice 40/40/40/64) — placeholders were flat.
- Currency coin/gem icons still use the placeholder PNGs (coin_gold/gem_pink) — they read fine.
